## 2. 모델 목적

`순매수 강도` 모델은 장중 필터 통과 종목 전체를 대상으로 다음 7개 항목을 점수화해서 총점이 높은 종목부터 줄을 세운다.

```text
순위 + 전일 순위 상승 + 거래대금/전일 거래대금 + 잔량비 + 순간강도 + 1분강도 + 프로그램/거래대금
```

핵심 목적은 단순 거래대금 상위가 아니라 다음 조건이 동시에 좋은 종목을 위로 올리는 것이다.

```text
전일 대비 돈이 새로 몰림
+ 매도잔량이 두꺼움
+ 체결강도가 강함
+ 1분 강도가 상승함
+ 프로그램 순매수가 거래대금 대비 진하게 들어옴
```

## 3. 전체 구조

| 구분 | 최종 설계 |
|---|---|
| 선발 대상 | 필터 통과 종목 전체 |
| 실제 종목 수 | 보통 100~200개 전후 |
| 화면 이름 | Top300 Pool |
| 실제 의미 | 최대 300개 이름표일 뿐, 실제 점수 계산은 필터 통과 N개 기준 |
| 총점 | 700점 |
| 항목 수 | 7개 |
| 항목별 만점 | 100점 |
| 등급 표시 | 총점 700점을 100점 환산 후 `A90`, `B84`, `C76`, `D60`처럼 표시 |
| 1차 점수화 방식 | 비례 점수화 |

## 4. Pool 배치와 갱신 속도

전체 종목을 `순매수 강도 총점` 기준으로 한 번 줄 세운 뒤, 순위에 따라 각 Pool에 배치한다.

| 순매수 강도 순위 | 표시 Pool | 갱신 Lane | 의미 |
|---:|---|---|---|
| 1~5위 | Top5 | HOT | 최우선 후보 |
| 6~20위 | Top15 | HOT | 집중 관찰 |
| 21~50위 | Top30 | MID | 후보 확장군 |
| 51위 이하 | Top300 Pool | POOL | 전체 감시군 |

개념은 다음과 같다.

```text
점수로 전체 줄세우기
→ Pool 배치
→ Pool에 따라 데이터 갱신 속도 결정
```

## 5. 점수 항목 최종안

| 번호 | 항목 | 계산 기준 | 점수 방식 | 현재 판단 |
|---:|---|---|---|---|
| 1 | 순위 | 현재 거래대금 순위 | 필터 통과 N개 기준 100~0점 비례 배점 | 현재 엔진 OK |
| 2 | 전일 | 전일순위 - 현재순위 | 상승폭 점수, 최대 100점 상한 | 현재 엔진 OK + 상한 필요 |
| 3 | 금액(억) | 오늘 거래대금 / 전일 거래대금 | 비율 높은 순으로 N개 기준 100~0점 비례 배점 | 전일 거래대금 TR/cache 필수 |
| 4 | 잔량비 | 매도잔량 / (매수잔량 + 매도잔량) × 100 | 계산값 그대로 0~100점 | 전용 계산 필요 |
| 5 | 순간강도 | 체결강도 | 체결강도 0~200을 0~100점으로 환산, 200 이상 100점 | 전용 계산 필요 |
| 6 | 1분강도 | 장중 1분강도 상승, 장마감 5분강도 proxy | 장중은 1분강도 상승 줄세우기, 장마감은 5분강도 0~200 선형 proxy | 전용 계산 필요 |
| 7 | 프로(억) | 프로그램 순매수 / 거래대금 | 순매수 0 이하 0점, 양수만 비율 순위로 100~0점 | 전용 계산 필요 |

## 6. 항목별 계산식

| 항목 | 계산식 | 비고 |
|---|---|---|
| 순위 점수 | `100 × (N - 현재순위) / (N - 1)` | N=1이면 100점 |
| 전일 점수 | `min(max(전일순위 - 현재순위, 0), 100)` | 100점 상한 필수 |
| 금액 점수 | `오늘 거래대금 / 전일 거래대금` 비율로 줄세운 뒤 100~0점 | 전일 거래대금 없으면 fallback 정책 적용 |
| 잔량비 점수 | `매도잔량 / (매수잔량 + 매도잔량) × 100` | 매도잔량 비율이 높을수록 점수 높음 |
| 순간강도 점수 | `min(max(체결강도, 0), 200) / 200 × 100` | 200 이상은 100점 |
| 1분강도 점수 | 장중: `one_min_strength_growth_rate` 또는 `one_min_strength_delta` 줄세우기, 장마감: `strength_5m` proxy | 5분강도는 `min(max(strength_5m,0),200)/200×100`, 100 이하는 0점 |
| 프로 점수 | `프로그램 순매수 / 거래대금` 비율로 줄세운 뒤 100~0점 | 프로그램 순매수 <= 0이면 0점 |
| 총점 | 7개 항목 합산 | 최대 700점 |
| 등급점수 | `round(총점 / 700 × 100)` | 화면 등급에 점수 반영 |

## 7. 등급 정책

등급은 100점 환산 점수를 기준으로 고정한다.

| 환산 점수 | 등급 | 예시 표시 |
|---:|---|---|
| 90점 이상 | A | `A90`, `A95` |
| 80~89점 | B | `B80`, `B89` |
| 70~79점 | C | `C70`, `C79` |
| 60~69점 | D | `D60`, `D69` |
| 60점 미만 | F | `F59` |

확정 원칙:

```text
90점 이상 A
89~80점 B
79~70점 C
69~60점 D
60점 미만 F
```

## 8. 1분강도 장중/장마감 정책

`1분강도`는 시간대에 따라 원천을 다르게 사용한다.

| 구분 | 원천 | 점수 방식 | 상태 표시 |
|---|---|---|---|
| 장중 | `one_min_strength_growth_rate` 우선, 없으면 `one_min_strength_delta` | 현재 필터 통과 종목군 안에서 상승값 줄세우기 | `ok` |
| 장마감/실시간 1분값 없음 | `strength_5m` | 5분강도를 0~200 기준으로 0~100점 환산, 100 이하는 0점 | `proxy` 또는 `proxy_nonpositive` |
| 둘 다 없음 | 없음 | 0점 | `missing` |

해석은 다음과 같다.

```text
장중에는 실제 실시간 1분강도 상승을 본다.
장마감에는 1분 실시간 bucket이 더 이상 의미 없으므로 5분강도를 조회해서 대체 proxy로 쓴다.
```

## 9. 전일 거래대금 확보 정책

전일 거래대금은 `금액(억)` 항목의 핵심 원천이다. 시총보다 장초반 효용 가치가 높으므로 반드시 확보해야 한다.

| 단계 | 처리 | 결과 |
|---:|---|---|
| 1 | 재접속/서버 시작 시 전일 거래대금 TR 조회 | 가장 우선 |
| 2 | TR 성공 시 runtime cache 저장 | 재접속 시 즉시 사용 |
| 3 | TR 실패 but cache 있음 | cache 사용 |
| 4 | 전일 거래대금 직접값 없음 | 전일 종가 × 전일 거래량으로 계산 |
| 5 | 전일이 휴일/거래정지 등으로 부적합 | 마지막 유효 거래일 거래대금 사용 |
| 6 | 모든 방법 실패 | 금액 항목 60점 고정 fallback |
| 7 | fallback 사용 시 | 화면/툴팁에 `전일대금 미확인 60점` 표시 |

중요 원칙:

```text
전일 거래대금 missing을 0으로 저장하지 않는다.
0은 실제 0이라는 뜻이므로 조회 실패와 혼동하면 안 된다.
최종 실패 시 0점이 아니라 60점 고정 fallback을 사용한다.
단, 화면에는 반드시 미확인 표시를 붙인다.
```

권장 row 필드:

| 필드 | 의미 |
|---|---|
| `prev_trade_value_eok` | 전일 또는 마지막 유효 거래일 거래대금 |
| `prev_trade_value_source` | TR/cache/계산값/마지막유효거래일/fallback |
| `prev_trade_value_status` | ok/cached/calculated/last_valid/fallback |
| `prev_trade_value_date` | 기준 거래일 |
| `prev_trade_value_fallback_score` | fallback 사용 시 60 |

## 10. 전일 거래대금 조회 실패 가능 원인

| 경우 | 설명 | 해결 |
|---|---|---|
| 로그인/세션 미완료 | Kiwoom 로그인 직후 TR 요청이 안정화되지 않음 | 로그인 완료 후 조회 시작, 재시도 큐 |
| TR 요청 제한/지연 | 100~200개 종목 조회 중 timeout/partial 가능 | cache 우선, 누락 종목만 순차 조회 |
| 휴일/월요일 날짜 문제 | 달력상 전일이 거래일이 아닐 수 있음 | 마지막 거래일 기준 사용 |
| 신규상장 | 전일 데이터가 실제로 없을 수 있음 | 신규상장 flag + fallback 60 |
| 거래정지 후 재개 | 직전 유효 거래일이 오래 전일 수 있음 | 마지막 유효 거래일 사용 |
| 종목코드 불일치 | `_AL`, `_NX`, 6자리 code 혼용 | 전일 데이터 key는 6자리 normalized code 고정 |
| TR 필드 단위 착오 | 원/천원/백만원/억원 혼동 가능 | 전일 종가 × 전일 거래량 교차검증 |
| cache 손상/삭제 | runtime 파일이 없거나 깨짐 | TR 재조회 후 cache 재생성 |
| 필터 종목 변경 | 새 종목이 Pool에 들어왔는데 cache에 없음 | 새 종목만 lazy TR 조회 |

## 11. 점수 안정성 정책

| 구분 | 최종안 |
|---|---|
| 1차 | 비례 점수화 적용 |
| 장점 | 미세한 차이 반영, 빠른 장초반 변화 포착 |
| 우려 | 화면 순위 흔들림 가능 |
| 대응 | 실제 운용 후 흔들림이 심하면 구간 점수화 전환 |
| 후속 안정화 | 2~3초 hold, 이동평균, Pool 승격/강등 hysteresis 검토 |

비례 점수화는 장초반 기회를 빠르게 잡는 데 유리하다. 다만 너무 흔들리면 구간 점수화로 바꾼다.

## 13. 최종 결론

`순매수 강도 v0.2`는 설정파일만으로 끝나는 기준이 아니라, 전용 점수 함수가 필요한 실전 선발 기준이다.

최종 구현 방향:

```text
전일 거래대금 확보
→ 7개 항목 100점씩 계산
→ 총점 700점 산출
→ 100점 환산 등급 표시
→ 총점 기준 전체 줄세우기
→ Pool 배치
→ Pool별 갱신 속도 적용
```
