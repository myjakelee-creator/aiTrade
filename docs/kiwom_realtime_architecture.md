# 키움 OpenAPI 09:00 폭주 데이터 실시간 처리 및 브라우저 표출 아키텍처 설계서

## 1. 개요 및 배경
증시 개장 직후인 **09:00 ~ 09:05** 사이에는 평소 트래픽의 수십에서 수백 배에 달하는 틱(Tick) 및 호가 데이터가 폭주(Spike)합니다. 키움 OpenAPI는 태생적으로 32비트 환경 및 단일 스레드 구조로 동작하기 때문에, 데이터 수신 이벤트 핸들러(`OnReceiveRealData`) 내에서 조금이라도 복잡한 계산 수식을 실행하면 즉시 지연(Latency)이 발생하고 HTS 이벤트 큐가 적체됩니다.

본 설계서는 이러한 한계를 극복하고, 폭주하는 데이터를 실시간으로 계산·선별하여 웹 브라우저에 0.1초 이내(무지연)로 표출하기 위한 **'수신 - 연산 - 전송 - 렌더링' 분리형 멀티프로세스 파이프라인 아키텍처**를 제안합니다.

---

## 2. 5단계 실시간 데이터 파이프라인 아키텍처

```
[키움 OpenAPI (32-bit)]
         │ (OnReceiveRealData - 연산 무조건 금지)
         ▼
[1. 초경량 수집기 (32-bit Python)]
         │
         │ IPC (ZeroMQ / InMemory PUB)
         ▼
[2. 고속 IPC 브로커 (ZeroMQ / Redis)]
         │
         │ 분배 (SUB)
         ▼
[3. 64-bit 연산 워커 (NumPy/Pandas 수식 필터링)]
         │
         │ 선별된 데이터 전송 (JSON/MsgPack)
         ▼
[4. 웹소켓 브로드캐스터 (FastAPI - 100ms 마이크로 배칭)]
         │
         │ WebSocket (Array Push)
         ▼
[5. 프론트엔드 렌더링 (Canvas / Lightweight Charts)]
```

### ① 1단계: 초경량 32-bit 수집기 (Data Ingestion)
* **목적:** 키움 OpenAPI로부터 뿜어져 나오는 원본 데이터를 누수 없이 가장 빠른 속도로 받아냅니다.
* **구현:** 키움 API 호환성을 위해 **32비트 파이썬 환경**으로 구축합니다.
* **핵심 규칙:** `OnReceiveRealData` 이벤트 내부에는 조건문이나 계산 수식을 절대 배치하지 않습니다. 오직 데이터를 수신하는 즉시 문자열 혹은 바이트 형태로 변환하여 고속 IPC 채널로 밀어내기만 합니다.

### ② 2단계: 초고속 프로세스 간 통신 (IPC 브로커)
* **목적:** 32비트 수집 프로세스와 64비트 연산 프로세스 간의 메모리단 초고속 데이터 전송.
* **기술 스택:** **ZeroMQ (ZMQ)** 또는 **Redis Pub/Sub**
* **특징:** 디스크 I/O가 전혀 발생하지 않는 인메모리(In-Memory) 방식으로 통신하며, 마이크로초(μs) 단위의 지연 시간으로 데이터를 라우팅합니다. 동일 장비 내 독립 프로세스 간 통신 시 ZeroMQ의 IPC/TCP 프로토콜이 가장 효율적입니다.

### ③ 3단계: 64-bit 연산 워커 (Calculation & Filtering)
* **목적:** 메모리 제약이 없는 환경에서 복잡한 투자 지표를 계산하고 화면에 뿌릴 가치가 있는 데이터만 선별합니다.
* **구현:** **64비트 파이썬(또는 C++, Go)** 독립 프로세스로 구동합니다.
* **동작 로직:** * ZMQ/Redis로부터 받아온 실시간 데이터를 고속 연산 라이브러리(**NumPy, Pandas**)를 활용해 수식 연산(예: 거래대금 급증 조건, 특정 호가 잔량 비율, 이동평균 돌파 등)을 수행합니다.
    * 조건을 만족하는 '선별된 핵심 데이터'만 웹 서버로 전달하고, 무의미한 노이즈 데이터는 여기서 즉시 폐기(Drop)하여 후속 파이프라인의 부하를 줄입니다.

### ④ 4단계: WebSocket 브로드캐스터 (Micro-Batching)
* **목적:** 수많은 브라우저 연결을 비동기로 유지하며 데이터를 최적화하여 전송합니다.
* **기술 스택:** **FastAPI (Python)** 또는 Node.js
* **핵심 로직 (마이크로 배칭):** 데이터를 틱 단위로 한 건씩 브라우저에 전송하면 브라우저에 과부하가 걸려 화면이 멈춥니다(DOM 프리징). 이를 막기 위해 서버 메모리 버퍼에 데이터를 **100ms(0.1초) 단위로 적재한 후, 배열(Array) 형태로 묶어서** 브라우저에 웹소켓(WebSocket)으로 Push합니다.

### ⑤ 5단계: 프론트엔드 Canvas 렌더링 (Browser View)
* **목적:** 초당 수십 번 넘어오는 데이터를 지연 없이 사용자의 화면에 시각화합니다.
* **기술 스택:** React / Vue.js + **Canvas 기반 그래픽 라이브러리** (예: TradingView Lightweight Charts, Apache ECharts)
* **핵심 로직:** 일반적인 HTML DOM 조작 방식은 브라우저 리렌더링 부하가 큽니다. GPU 가속을 활용하는 HTML5 Canvas 기술을 이용해 웹소켓으로 들어온 배열 데이터를 차트에 다이렉트로 매핑하여 그리도록 구현합니다.

## 3. 핵심 성공 요인 (Key Success Factors)

1.  **물리적 프로세스 격리 (Decoupling):** 키움 수집기, 연산기, 웹 서버를 하나의 프로그램 안에서 실행하지 않고 독립된 프로세스로 쪼개어 배치해야 파이썬의 GIL(Global Interpreter Lock) 한계를 극복하고 CPU 멀티코어를 백분 활용할 수 있습니다.
2.  **계산과 전송의 철저한 분리:** 지표 계산, 필터링 등 무거운 비즈니스 로직은 브로드캐스팅 서버가 아닌 전용 '연산 워커'에서만 수행해야 전송 지연이 발생하지 않습니다.
3.  **마이크로 배칭 (Micro-Batching):** 인간의 눈이 인지할 수 있는 한계(약 100ms)에 맞춰 데이터를 버퍼링하여 전달함으로써 브라우저의 연산 부담을 최소화합니다.
4.  **커넥션 풀링 및 세션 유지:** 데이터베이스나 외부 시스템 연결 시 미리 연결을 맺어두는 구조(Connection Pool)를 필수적으로 유지하여 09:00 정각에 세션 수립으로 인한 지연을 차단합니다.
